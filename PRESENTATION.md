## 2. Слайд: цель проекта

- **Что**: браузерная пошаговая RPG «Jurassic Cycle» — игрок выбирает один из 6 видов
  динозавров (3 хищника, 3 травоядных) и ход за ходом проводит его через 4 стадии взросления
  (Детёныш → Молодой → Подросток → Взрослый).
- **Цель игрока**: выжить и дойти до взрослой стадии.
- **Ключевое ограничение**: всё работает в браузере — **без сервера и без базы данных**;
  состояние хранится в `localStorage` и экспортируется в JSON.

**Тезис для рассказа:** «Мы хотели маленькую, но законченную игру с честной механикой и
аккуратным интерфейсом, которую можно открыть где угодно офлайн».

## 3. Слайд: как велась работа (методология)

### Spec-driven через OpenSpec

Каждая задача оформлялась как **change** в `openspec/changes/<имя>/`:

- `proposal.md` — «почему» и «что меняем»;
- `design.md` — решения и компромиссы;
- `specs/<capability>/spec.md` — требования в формате MUST + сценарии WHEN/THEN;
- `tasks.md` — чек-лист реализации.

Схема цикла:

```
proposal → specs → tasks → реализация → validate --strict → коммит/PR → archive (sync specs)
```

**К чему приводило:** требования фиксировались до кода, а после завершения команда
`openspec archive` переносила change в архив и **синхронизировала главные спецификации**
(`openspec/specs/`). То есть по коду всегда есть «источник правды» о том, *почему* он такой.

### Роль ИИ-агента (Qwen Code)

- **Qwen Code** — CLI-агент, который вёл разработку: читал код, писал и правил файлы,
  запускал сборку и тесты, гонял Docker, коммитил и открывал PR.
- **Инструменты агента**: чтение/поиск/правка файлов, запуск команд, браузерный инструментарий,
  работа с git и GitHub CLI (`gh`).
- Пользователь выступал **владельцем продукта**: ставил задачи, принимал решения по геймплею
  и интерфейсу, проверял результат в браузере.

**Тезис для рассказа:** «ИИ-агент не заменял архитектора — он быстро и аккуратно реализовывал
спецификацию под контролем человека, а человек принимал продуктовые решения».

## 4. Слайд: технологический стек

| Слой | Технология | Зачем |
| --- | --- | --- |
| UI | React 18 + TypeScript | компонентный интерфейс, строгая типизация |

| Упаковка | Docker + nginx | раздача собранного SPA |
| CI/CD | GitHub Actions | тесты, сборка, публикация на GitHub Pages |

## 5. Слайд: архитектура — игровое ядро отдельно от интерфейса

- **`src/game/` — чистое ядро без зависимостей от React.** Функции работают над неизменяемым
  состоянием и возвращают новое.
  - `engine.ts` — механика хода: действие → расход ресурсов → рост → смерть/победа.
  - `balance.ts` — все числовые константы баланса.
  - `species.ts`, `events.ts`, `actions.ts` — каталоги видов, событий и действий.
  - `rng.ts` — **детерминированный ГПСЧ**, состояние которого хранится в сохранении
    (любой ход воспроизводим).
  - `save.ts` — сериализация, `localStorage`, экспорт/импорт, валидация.
- **`src/state/`** — редьюсер и React-контекст.
- **`src/components/`** — экраны и панели; **`src/ui/`** — карта SVG-моделей.

**К чему приводило:** логику можно тестировать без браузера (окружение `node`), а интерфейс —
менять, не рискуя сломать механику.

## 7. Слайд: графика — SVG вместо спрайтов

- В `src/dino_svg/` лежат **24 SVG** — по 4 стадии на каждый из 6 видов.
- Модели подключаются картой `import.meta.glob` в `src/ui/dinoArt.ts` (вид + стадия → URL).
- Модели — чёрные силуэты, поэтому на тёмной сцене перекрашиваются CSS-фильтром.
- В меню выбора показываются **взрослые** модели каждого вида.

**К чему приводило:**
- сначала тираннозавр отображался без картинки — причина оказалась в именах файлов
  (`trex_*`, а не `tyrannosaurus_*`); исправлено картой префиксов;
- отказ от внешних ассетов и CDN сохранил требование «работает офлайн».

## 8. Слайд: оживление интерфейса

- **Сцена:** в покое динозавр по центру; **при угрозе** динозавр уходит влево, противник
  (тоже SVG) появляется справа.
- **Эффекты действий:** лужица воды после удачного питья, листва при поиске пищи, компас при
  исследовании, метка цели при охоте, «z-z-z» во сне.
- **Анимация урона:** динозавр «шатается», причём **чем меньше здоровья, тем медленнее и
  заметнее** качание (длительность и амплитуда задаются CSS-переменными от отношения
  `health / maxHealth`).
- **Стабильный интерфейс:** при нуле энергии кнопки действий **не исчезают**, а становятся
  неактивными — раскладка не «скачет».

**К чему приводило:** обратная связь на каждое действие усилила «ощущение игры», а решение
«показывать, но блокировать» кнопки убрало дёрганье панели.

---

## 9. Слайд: баланс через симуляцию (инженерный приём)

- **Автотест-симуляция**: наивный «автопилот» играет ~200 партий на каждый вид, и тест
  проверяет долю побед (`balance.test.ts`).
- **Целевые диапазоны:** хищники — 45–65% побед, травоядные — 85–95%.
- По ходу работы баланс ломался дважды:
  - травоядные выигрывали 100% (не сталкивались с угрозой) — добавили риск засады при сборе;
  - правило нулевой энергии «зацикливало» тестовый автопилот (поиск→отдых→голод) — автопилот
    научили уходить в сон при нуле энергии.
- Каждое изменение проверялось прогоном симуляции, а не на глаз.

**К чему приводило:** винрейты были возвращены в целевые диапазоны, и теперь **любое** будущее
изменение баланса ловится автотестом, а не вручную.

## 10. Слайд: Docker и доставка

- **`Dockerfile`** — многоступенчатая сборка: Node собирает `dist`, **nginx** его раздаёт.
- **`nginx.conf`** — SPA-fallback (`try_files … /index.html`), gzip, длинный кеш ассетов.
- **`docker-compose.yml`** — сервис `web`, порт `8080`, `HEALTHCHECK`.
- **GitHub Actions** — на пуш в `main` прогоняет тесты, сборку и публикует на GitHub Pages.

Проверено вживую: образ собирается, контейнер поднимается со статусом `healthy`, страница и
SVG-ассеты отдаются (`HTTP 200`).

**Тезис для рассказа:** «Проект не только написан, но и упакован — его можно запустить одной
командой `docker compose up --build`».

## 11. Сценарий демо (5 минут)

1. `npm run dev` → открыть меню, показать **взрослые SVG** всех 6 видов.
2. Начать партию за хищника, сделать несколько ходов: показать эффекты (питьё → лужа,
   сон → «z-z-z»), индикатор стадии и трек стадий слева.
3. Довести до схватки: показать, как динозавр уходит влево, противник — вправо, и как после
   победы дают **пищу** («съели добычу»).
4. Показать качание при уроне и уменьшение активности кнопок при нуле энергии.
5. Отдельно — `docker compose up --build` и открытие `http://localhost:8080`.
6. Показать `npm test` (41 тест) и `openspec list` (изменений нет — всё синхронизировано).

## 12. Слайд: чем всё закончилось (итог)

- **Продукт:** законченная браузерная игра — 6 видов, 4 стадии, живая сцена, эффекты,
  выживание, сохранения, экспорт/импорт.
- **Качество:** 41 автотест (ядро, схватка, выживание, баланс, сохранения), строгая типизация,
  зелёная сборка.
- **Процесс:** каждое изменение зафиксировано в спецификациях OpenSpec и заархивировано;
  главные спеки синхронизированы.
- **Доставка:** Docker-образ + GitHub Pages; код опубликован в репозитории `Loncelo1/jurassic-cycle`.

### Что было сложно и как решали

| Трудность | Решение |
| --- | --- |
| Баланс «плыл» после правок | симуляция ~200 партий на вид + автотест винрейтов |
| Тираннозавр без картинки | карта префиксов имён файлов (`trex_*`) |
| Кнопки «прыгали» при нуле энергии | показывать всегда, блокировать неактивные |
| Локальная проверка Docker | запуск Docker Desktop, проверка через `compose`/`healthcheck` |

### Чему научились

- Spec-driven подход окупается на длинной дистанции: «почему» остаётся в спецификациях.
- Игровой баланс надо **измерять**, а не настраивать интуицией.
- Изоляция игрового ядра от React делает и тесты, и правки UI безопасными.

## 13. Вероятные вопросы и ответы

- **Почему без сервера?** Так проект проще запускать, он работает офлайн и не требует
  инфраструктуры; Docker здесь — только для удобной раздачи готовой сборки.
- **Почему эмодзи/силуэты, а не спрайты?** Меньше зависимостей, офлайн-работа, быстрая итерация.
- **Как гарантировать честность случайности?** Детерминированный ГПСЧ, состояние которого
  лежит в сохранении, — партия воспроизводима.
- **Как проверялся UI?** Вручную в браузере пользователем (агент не снимал скриншоты);
  логика — автотестами.
- **Что дальше?** Пошаговые схватки с приёмами, биомы/погода, прокачка навыков, звук.
